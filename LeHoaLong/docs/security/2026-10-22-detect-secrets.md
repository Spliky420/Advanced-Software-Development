# Secrets — detect-secrets — 2026-10-22

**Tool:** detect-secrets 1.5.0, all 27 default plugins (AWS, Azure, GitHub,
private keys, JWT, high-entropy strings, secret keywords, ...)
**Scope:** all 366 files tracked by git, except `package-lock.json`
**Result:** **0 findings.** The baseline (`.secrets.baseline`, repo root) is
empty, so any finding at all blocks a commit.

## Why `package-lock.json` is excluded

It is full of `integrity` hashes (`sha512-...`), which are high-entropy by
design and would bury anything real. It is generated by npm, not written by
anyone, so a secret cannot plausibly be typed into it.

## Proving the scan is live

A clean result is only worth something if the scanner would have caught a
real one, so two canaries were planted and scanned with the same settings:

| Canary | Detected as |
| ------ | ----------- |
| `aws_access_key_id = "AKIAIOSFODNN7EXAMPLE"` | AWS Access Key | <!-- pragma: allowlist secret -->
| `password = "hunter2-Sup3rS3cret!"` | Secret Keyword | <!-- pragma: allowlist secret -->

Planted inside `LeHoaLong/backend/app/` with the hooks installed, the AWS
canary blocked the commit (`ERROR: Potential secrets about to be committed`).
Both canaries were deleted afterwards and never committed.

## Manual cross-check

A `git grep` for `password|secret|api_key|token` assigned a quoted value of
six or more characters found one line:

```
mcp-server/routes/ai_mode.py:16: _client = OpenAI(base_url=OLLAMA_BASE_URL, api_key="ollama")
```

This is not a secret. The OpenAI-compatible client requires a non-empty key,
and Ollama ignores it. The `base_url` is local Ollama, so no request goes to
OpenAI, which keeps it within CLAUDE.md's "only Ollama" rule. It is in the
shared `mcp-server/`, so it is reported here, not changed.

## How the repo keeps secrets out

- `.env` is gitignored, and only `.env.example`, with no secrets, is tracked.
- Nothing in Release 0–2 needs a credential: Ollama, MCP, RAG and the
  multi-agent server are unauthenticated local processes.
- The Azure deployment (Release 2, step 8) is designed to use OIDC
  federation, so the workflow will hold no client secret either.

## Pitfall found while generating the baseline

The first baseline was generated from Git Bash, which rewrote the exclude
regex `(^|/)package-lock\.json$` into `(^|C:/Program Files/Git/)package-lock/.json$`
before detect-secrets saw it. The baseline recorded that pattern, which would
never match on any teammate's machine. It was regenerated with
`MSYS_NO_PATHCONV=1`, and the committed baseline holds the correct pattern.
